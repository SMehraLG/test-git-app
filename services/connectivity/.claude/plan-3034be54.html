Plan: Customer connectivity score endpoint

Summary

Implement GET /api/v1/customer/{customer_id}/connectivity-score in the FastAPI connectivity service (services/connectivity). A pure scoring module normalises download speed (fact_httpget.speed_mbps vs provisioned_mbps), upload speed (fact_httppost.speed_mbps vs provisioned_mbps), and latency (fact_udplatency.rtt_avg_ms vs a configured target) to 0-100 sub-scores, combines them 50/30/20, applies upper-inclusive bands (>=80 excellent, 60-<80 good, 40-<60 degraded, <40 critical), and reweights proportionally when a metric type is absent. A score service issues operator-scoped, 30-day partition-pruned BigQuery aggregation queries and delegates to the scorer; the route returns a derived-only DTO or 404 when no measurements exist. A minimal security module adds API-key auth, per-IP rate limiting, and PII redaction so the new route matches the service baseline and honours GDPR/per-OpCo obligations.

Linked spec

spec-7aeea9f3 — Customer connectivity score endpoint

Tasks

  • T-01: Add pure scoring module: normalisation, 50/30/20 weighting, upper-inclusive bands, proportional reweighting

New module src/connectivity/scoring.py with pure, I/O-free functions. Normalise each metric to a 0-100 sub-score: speed metrics as capped ratio of measured to provisioned throughput; latency as measured rtt against a configured latency target (lower is better). Combine sub-scores with fixed weights download=0.5, upload=0.3, latency=0.2. Derive the status label with upper-inclusive bands (>=80 excellent, 60-<80 good, 40-<60 degraded, <40 critical). When one or two metric types are absent, renormalise the present weights so they sum to 1 and score on those only. Deterministic: no clock/random inputs. Weights and band thresholds are module constants, not request-configurable.

  • T-02: Add score response DTO models projecting only derived/aggregate fields

New module src/connectivity/models/score.py with Pydantic response models: overall score (0-100), status label, window bounds (start/end), per-metric block (sub_score + sample_count) for download/upload/latency, and an echo of the supplied customer identifier. The DTO exposes only derived/aggregate values; it has no field for raw measurement rows, device/line identifiers, or internal operator identifiers, enforcing data minimisation at the serialisation boundary.

  • T-03: Add security module: API-key auth dependency, per-IP rate limiter, and structlog PII-redaction processor

New package src/connectivity/security/ providing: (a) a FastAPI dependency that validates an API key by SHA-256 hash with constant-time comparison, active only when CONNECTIVITY_API_KEY_ENABLED is true; (b) a per-IP token-bucket rate limiter (60 tokens, 10s refill) applied as a dependency/middleware, gated by CONNECTIVITY_RATE_LIMIT_ENABLED; (c) a structlog processor that redacts/omits customer_id (and other PII keys) from log events before the JSON sink. Reusable across /api/v1 routes so the new endpoint introduces no weaker access path.

  • T-04: Add settings fields for auth, rate limiting, operator-key mapping, and latency target

Extend src/connectivity/config/settings.py (CONNECTIVITY_ prefix) with: api_key_enabled (bool, default false), api_key_sha256 (hashed key), rate_limit_enabled (bool, default true) plus bucket capacity/refill, an api-key-to-operator/market mapping used to derive request operator scope, and latency_target_ms used by the scorer. No secrets committed; production values arrive as Cloud Run env vars from Secret Manager.

  • T-05: Add score service: operator-scoped, partition-pruned BigQuery aggregation delegating to the scorer

New module src/connectivity/services/score_service.py. Resolve the operator/market from the authenticated request context (api-key->operator mapping) and inject it as a mandatory predicate. For each of fact_httpget, fact_httppost, fact_udplatency, issue a parameterized BigQuery aggregation query filtered by customer_id, a trailing-30-day dtime_utc cutoff (partition pruning), and the operator predicate, projecting only AVG(speed_mbps)/AVG(provisioned_mbps)/AVG(rtt_avg_ms) and COUNT plus min/max dtime for the window. Apply defensive in-memory re-filtering on customer_id/window/operator so results are correct even against an adapter that ignores query params (the mock). Pass the aggregates to scoring.py. Raise a not-found signal when all three counts are zero. The customer_id path parameter is treated as an opaque measurement-lookup token: it is used only as a query filter value and is never joined against or resolved through any internal operator/customer identity table (no TCId or identity resolution is performed).

  • T-06: Add and register the connectivity-score GET route wiring auth, rate limit, operator scope, and score service

New module src/connectivity/api/routes/score.py exposing GET /api/v1/customer/{customer_id}/connectivity-score under an APIRouter(prefix=/api/v1). Wire the API-key auth dependency, the per-IP rate limiter, the operator-context dependency, and the get_bq_adapter dependency; call the score service; return the DTO on success and a 404 (customer identified) when the service reports no measurements. Register the router in src/connectivity/main.py create_app().

  • T-07: Add unit and integration tests and confirm the 80% branch-coverage gate

Add tests/test_scoring.py (unit, mocked/no I/O) covering normalisation, 50/30/20 weighting, boundary values at exactly 40/60/80, proportional reweighting for 1-2 metric types, and determinism; and tests/test_score_endpoint.py (integration, @pytest.mark.integration) driving the endpoint via httpx AsyncClient with get_bq_adapter overridden by a stub returning controlled aggregates: scored response, 404 on no measurements, partial-metric reweighting, per-operator isolation, auth enforced when enabled, and customer_id absent from emitted logs. Keep the default suite fast (mock the adapter) and ensure uv run pytest --cov --cov-branch --cov-fail-under=80 passes in services/connectivity.

  • T-08: Add load/performance test asserting p95<1s and p99<2s at 2x expected peak

Add a performance/load test that owns the test_strategy performance scenario: drive the connectivity-score endpoint at 2x expected peak concurrent load against a production-like staging dataset (anonymised) and assert p95 < 1s and p99 < 2s inclusive of the 30-day aggregation. Runs in the CI performance stage, not the default unit/integration fast run.

Test strategy

Gherkin scenarios

G-01 — task T-01

  • Given a composite score of exactly 80, then exactly 60, then exactly 40
  • When the status label is derived
  • Then the labels are excellent, good, and degraded respectively (upper-inclusive bands), and a score below 40 yields critical

G-02 — task T-01

  • Given a customer with only download and latency sub-scores available (no upload)
  • When the composite score is computed
  • Then the download and latency weights are renormalised to sum to 1 (0.5 and 0.2 -> ~0.714 and ~0.286) and the score uses only those two metrics

G-03 — task T-01

  • Given measured throughput greater than or equal to provisioned throughput
  • When the speed metric is normalised
  • Then the sub-score is capped at 100 and never exceeds it

G-04 — task T-01

  • Given an identical set of per-metric aggregates
  • When the score is computed multiple times
  • Then the numeric score and status are identical every time (deterministic)

G-05 — task T-02

  • Given a successfully scored customer
  • When the response is serialised
  • Then the payload contains only the customer identifier echo, score, status, window bounds, and per-metric sub_score plus sample_count, and contains no raw measurement rows or internal device/line/operator identifiers

G-06 — task T-05

  • Given the customer has measurements dated both within and older than the trailing 30-day window
  • When the score service aggregates measurements
  • Then only measurements within the 30-day window contribute to the sub-scores

G-07 — task T-05

  • Given a customer with no measurements of any type in the 30-day window
  • When the connectivity score is requested
  • Then the endpoint returns a 404 not-found response that identifies the customer, not a score

G-08 — task T-06

  • Given a customer identifier that exists under operator B while the request is authenticated as operator A
  • When the connectivity score is requested
  • Then operator B measurements are never returned or reflected in the score (the request is scoped to operator A only)

G-09 — task T-06

  • Given CONNECTIVITY_API_KEY_ENABLED is true
  • When the endpoint is called with a missing or invalid API key, then with a valid key
  • Then the invalid call is rejected before any measurement query and the valid call returns the scored response

G-10 — task T-03

  • Given a request carrying a customer identifier
  • When the handler emits structured logs
  • Then the customer_id value does not appear in the emitted log records

Coverage notes

Unit tests mock the BigQuery adapter and exercise scoring.py directly; integration tests drive the endpoint via httpx AsyncClient with get_bq_adapter overridden by a stub. CI gate: uv run pytest --cov --cov-branch --cov-fail-under=80 in services/connectivity; >=90% coverage target on changed code. Integration tests are marked @pytest.mark.integration and segregated from the default fast run per CASAS pytest conventions.

Performance tests

  • Load test the endpoint at 2x expected peak concurrent load asserting p95 < 1s and p99 < 2s inclusive of the 30-day aggregation, against a production-like staging dataset with anonymised data.

NFR mechanisms

  • Meet the p95<1s / p99<2s budget by issuing parameterized BigQuery aggregation queries with a trailing-30-day dtime_utc partition-pruning predicate so only in-range day-partitions of the fact tables are scanned, and computing AVG/COUNT server-side rather than fetching raw rows.
  • Guarantee determinism (same inputs -> same score) using fixed weight constants (0.5/0.3/0.2), deterministic proportional reweighting, and upper-inclusive band thresholds, with no clock- or random-dependent input beyond the request-time window bound.
  • Enforce GDPR data minimisation by projecting only aggregate/derived columns in the BigQuery SELECT and serialising a response DTO with no fields for raw measurement rows, device/line identifiers, or internal operator identifiers.
  • Enforce per-OpCo isolation by deriving the operator/market from the authenticated API key and injecting it as a mandatory WHERE predicate on every measurement query (query-side, not post-fetch), so a customer_id collision across operators cannot resolve another operator's data.
  • Preserve auth and rate-limit parity by applying the SHA-256 constant-time API-key dependency (gated by CONNECTIVITY_API_KEY_ENABLED) and the per-IP token-bucket limiter (60 tokens / 10s refill) to the new route, and redacting customer_id from structlog output via a PII-redaction processor.
  • Expose the endpoint only behind the UC-C-004 API gateway, which enforces OAuth 2.0/OIDC per-consumer authorisation upstream using each market's per-OpCo OAuth provider configuration (CON-004-02); the service-level SHA-256 constant-time API-key dependency is the second defence-in-depth layer, so the route is never reachable without gateway auth.
  • Run the Cloud Run container as a non-root user (Dockerfile USER directive) so the new endpoint inherits the platform's non-root execution baseline.
  • Emit structured JSON logs enriched with Cloud Trace-correlated trace and span IDs plus request metadata (method, path, status, latency), and propagate OpenTelemetry spans to Cloud Trace for the new route, matching the service observability baseline (customer_id stays redacted via the PII processor).

Rollout / Migration / Rollback

Rollout

Deploy through the existing Horizon v2 per-service path-filtered GitHub Actions workflow for services/connectivity: build an image tagged with the commit SHA, push to Artifact Registry via Workload Identity Federation (no key files), and roll out on Cloud Run as a canary 0% -> 10% -> 50% -> 100% with /health and /ready smoke-test gates between steps. The new GET route is purely additive, so no existing traffic path changes. API-key auth stays disabled in dev (CONNECTIVITY_API_KEY_ENABLED=false) and enabled in production behind the API gateway.

Migration

n/a - no schema or data migration. The endpoint only reads existing SamKnows fact tables (fact_httpget, fact_httppost, fact_udplatency); it adds no columns and writes no rows. New configuration (hashed API key, rate-limit params, api-key->operator mapping, latency target) is delivered as Cloud Run env vars sourced from Secret Manager, never committed to Git.

Rollback

Roll back by promoting the previous Cloud Run revision (the prior immutable image digest retained in Artifact Registry), target <15 minutes; because the change is an additive, read-only GET route with no migration, rollback is a pure revision switch with no data cleanup and the route simply disappears. Rollback triggers: sustained endpoint error rate >1% or p99 >2s. Designated rollback owner: the connectivity service on-call/service owner initiates and verifies the revision switch. The rollback path is rehearsed in dev/staging before any production promotion (revert-to-previous-revision drill run as part of the canary gate). The route can additionally be disabled without a redeploy by toggling its registration/config flag off.

Reviews

Cost notes

Marginal cost is one BigQuery aggregation query per request over at most 30 day-partitions across up to three fact tables, bounded by the p95<1s budget via partition pruning. No new always-on infrastructure: reuses the existing Cloud Run service and BigQuery dataset.

Security notes

Adds a read surface keyed by customer_id (personal data). Mitigated by defence-in-depth: the route is reachable only behind the UC-C-004 API gateway (OAuth 2.0/OIDC per-consumer auth, per-OpCo OAuth provider config CON-004-02) plus a service-level SHA-256 constant-time API-key dependency, per-IP rate limiting, query-side operator scoping, PII redaction in logs, non-root container execution, and a response DTO that leaks no internal identifiers.

Privacy notes

customer_id is personal data under GDPR; processing is minimised to a 30-day derived aggregate with no raw records returned, customer_id redacted from logs, and access isolated per operator/market.

Data notes

Reads existing day-partitioned fact tables and aggregates AVG(speed_mbps)/AVG(provisioned_mbps)/AVG(rtt_avg_ms) and COUNT within the window; performs no writes and creates no tables. The customer_id is an opaque query-filter token, never joined against or resolved through an internal identity table (no TCId resolution). Operator/market scope is a mandatory query-side predicate sourced from the authenticated context, never from customer_id.

Infra notes

No new infrastructure resources; deploy via the existing Terraform-managed Cloud Run service and per-service CI workflow, with secrets from Secret Manager and non-root container execution. The existing /health and /ready probes are reused as canary smoke-test gates. Observability: structured JSON logs with Cloud Trace-correlated trace/span IDs and request metadata, plus OpenTelemetry spans exported to Cloud Trace. Rollback is rehearsed in staging with a designated service-owner as rollback owner.

Mitigations

  • Operator scope is enforced as a mandatory query-side WHERE predicate, not post-fetch filtering, so a Python-side bug cannot leak cross-operator data.
  • Defensive in-memory re-filtering on customer_id/window/operator guards against an adapter that returns extra rows (e.g. the in-memory mock).
  • Auth and rate-limiting are attached as route dependencies so the endpoint cannot be served without them when enabled.
